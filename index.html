nix-reflect

A parser and an evaluator for the Nix language, written in Nix. parser.parse turns a string of Nix into a tree of attribute sets that you can inspect and rewrite, and eval reduces that tree to a value, with scopes, lazy thunks and typed errors implemented in Nix itself.

Because the whole thing is ordinary Nix code, it runs wherever nix eval does, and a Nix program can use it to read, transform and run Nix source as data. It is a work in progress: the last section measures how much of the language it handles today.

parser.parse :: string → AST

Parsing

The parser is built from nix-parsec, a parser-combinator library written in Nix. There is one small parser per construct (integers, strings, paths, lists, attribute sets, lambdas, let, with and so on), alternatives are tried with choice, and binary operators are layered by precedence from * and / down to ||, so 1 + 2 * 3 groups the way Nix groups it.

Every parser is wrapped so that the node it produces records the offset and the text it matched. Parsing " 1 + 2" gives a binaryOp node whose source is:

"1   +   2"

A node is an attribute set: a nodeType, its fields (lhs, op, rhs; bindings and body; param; …), the source text in __src, and mapNode and fmap for producing changed copies. Nothing is hidden behind a function, so a tree can be printed, compared, walked or rebuilt with ordinary Nix. true, false and null are not literals: they parse as identifiers and are looked up in scope, as in Nix.

eval :: string | AST → value

Evaluating

The evaluator walks the tree with one function per node type (evalLetIn, evalWith, evalLambda, evalApplication, …). Each returns a computation in an evaluation monad that the library defines for itself, in its own words "roughly an ExceptT EvalError (StateT EvalState m) stack": a step can read and update the evaluation state, or stop with an error, and the plumbing between steps is written once. The library also implements a do notation for these computations, so evaluation functions read as a sequence of named steps rather than nested callbacks.

Laziness

Nix only evaluates what a result needs, so the evaluator does too. A binding becomes a thunk: the AST node, the scope at the point it was created, and an ID. Forcing a thunk looks it up in the cache held in the evaluation state; the first force evaluates it and stores the value, later ones reuse it. Because Nix values are immutable, "storing" means returning a new state, which the monad passes on.

eval evaluates as far as the outermost value (weak head normal form), as Nix does; eval.strict forces everything, which is what printing a whole list or attribute set needs.

Errors

eval.either returns Right value or Left error, where the error is one of a fixed set of kinds: Throw, Abort, AssertError, TypeError, UnknownIdentifierError, MissingAttributeError and a few internal ones. eval returns the value, or throws the error. A missing attribute under or is caught, so { a = 1; }.b or 42 is 42.

eval.either "1 + \"a\""
Left EvalError.TypeError:
  Incorrect types for binary operator +:
          1 and "a"
            (expected one of [ [ "int" "float" ] [ "string" "path" ] ])

mapNode · eval.eval.store

Code as data

Because a parsed expression is plain data, it can be rewritten before it is run. This swaps the operands of 1 + 2 and turns the + into a -, giving 2 - 1:

let
  ast = parser.parse "1 + 2";
  swapped = ast.mapNode (n: n // {
    op = "-"; lhs = n.rhs; rhs = n.lhs;
  });
in eval swapped
1

There is also a second, much simpler evaluator. eval.eval.store writes the text into the Nix store with a derivation and imports the result, so the real Nix evaluator does the work. It is fast and exact, but it needs import-from-derivation, and it offers none of the inspection the AST evaluator does.

eval.eval.store "1 + 1"
2

What is missing

  • Syntax: the ? and -> operators, args@{ … } patterns, nested paths in bindings (a.b.c = 1) and identifiers containing ', such as foldl', do not parse yet.
  • Evaluation: string interpolation fails inside the evaluator; builtins such as map cannot yet call a function defined in the evaluated code; and list elements are evaluated eagerly, so one throw in a list fails the whole list where Nix would not care.
  • Functions from text: eval.fn, which builds a callable function from text and can rewrite its text or AST, fails on the current main branch: it expects eval to return an Either, and eval now returns the bare value.

Speed

Interpreting Nix in Nix is slow. Every step of the evaluated program is several monadic binds, each building new attribute sets for the state, inside an evaluator that is itself interpreted. A naive fib 7 takes most of a minute (the table has the measured time), and deep recursion exhausts the host evaluator's stack: fib 10 fails with a stack overflow even with Nix's call-depth limit raised.

That is fine for what the library is for, reflection over small expressions and configuration, and it is the obvious place for future work: a cheaper state representation or fewer binds per node.

flake

Using it

Add the flake as an input and use its lib output:

inputs.nix-reflect.url = "github:harryaskham/nix-reflect";

# in your outputs
with inputs.nix-reflect.lib.${system};
eval "let x = 2; in x * 21"   # 42

Or try it from a shell. Raise Nix's call-depth limit; the evaluator recurses deeply.

nix eval --option max-call-depth 1000000 \
    --apply 'lib: lib.eval "let x = 2; in x * 21"' \
    github:harryaskham/nix-reflect#lib.x86_64-linux
42

In a checkout, direnv provides run-tests (all suites, or one, such as run-tests eval.ast) and with-lib for evaluating against the library.
